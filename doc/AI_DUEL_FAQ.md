## F1 对战房多久没动作会被自动关闭？

**没有「战斗内倒计时强制收房」的秒级机制，而是惰性回收**：某次访问（玩家轮询 / 管理端列表）触发检查时，发现满足下述任一条件才真正摘除并关房。

| 场景 | 时限 | 说明 |
|---|---|---|
| `waiting` 且**一直无人 join 客队**（`awayUid` 为空） | 建房后 **10 分钟** | 建房方没等到对手就被回收 |
| 已开赛（`live`）但**双方都没有任何局面帧推进** | 最后一帧后 **10 分钟** | 心跳/**在线状态不算活跃**，人挂着不动手也会被判空闲 |
| 双方均离线、比赛不活跃 | 沿用 30s 心跳超时判定 | 双离线且无帧 → 自动回收 |

> ⚠️ 空房或静默房的**实际暴露可能晚于 10 分钟**：因为回收是「访问时顺带查」，一旦期间无人访问该房，要等下一次访问（或彻底无人访问）才被摘除。

**关房后怎么知道 / 怎么办**

- 用户 / 机器人的 `state` 返回 `room_status:"closed"`；
- 机器人服务收到 `event:"room_closed"`（`reason` 含 `timeout`/`idle`/`no_activity`/`stale`/`inactive`）即应停止走棋并释放会话；
- **对策**：建房后若很快就需要对手 / 对局，不要在 `waiting` 干等 —— 见 **F5** 明确指定对手或平台 AI。

## F2 道具明明还能用，为什么 `op:"item"` 反复返回 `condition_failed / skills_exhausted`？

**这是每半局的技能配额机制，不是异常，也不是被恶意拦截。**

| 项 | 说明 |
|---|---|
| 额度 | 每半局技能 **3 次**（`items.rules.skills_per_half`），**被动【棒】也会计次** |
| 用满后 | 再 `op:"item"` → 服务端返回 `condition_failed` + `reason_detail:"skills_exhausted"`，**不扣库存** |
| 何时恢复 | **换边时服务端自动重置**额度，下一半局即可再用 |

**最常见的一个真 bug（踩坑总结）**：接入方把 `skills_exhausted` 当成异常，连续失败后把 `item` **整局熔断**（`banned=['item']`），导致「之后整局再不用道具」—— 但其实只是当前半局额度满了。

**正确做法**

1. 用 `items.half_used.count >= items.rules.skills_per_half` 本地**提前判断满额**，满了这半局就别再 `item`；
2. 万一仍收到 `condition_failed/skills_exhausted`（可能因为 `state` 快照滞后，见下），**让位当前半局即可，不要整局禁用**，换边自动恢复；
3. 【令】`ling` 例外：掷骰「传令成功」会由服务端重置本半局额度，满额后可留意是否仍走 `ling`。

> **关于 state 快照滞后**：某次操作（如 `sac`）成功后，返回的 `items.half_used.count` 可能仍是**旧值**（快照未及刷新），本地会「以为还没满」再选 `item`，于是多收到一次 `skills_exhausted`。这种残余窗口**以服务端报错为准**，一见报错就让位即可，别依赖滞后快照反复踩。

相关字段：`items.half_used` / `items.rules.skills_per_half` / `items.stock` / `items.bat_armed`。详见 [AI_DUEL_API.md §4.5.1](./AI_DUEL_API.md)。

## F3 打了几场，roll 结果好像一边倒（某场狂安打、某场狂出局），是不是概率表有问题？

**多数是小样本方差，属正常（二项式涨落）**，不是引擎偏袒或概率表错误。

- 3 局制每边只有几个打席量级，序贯抽查的局间方差很大：一场「安打系连发 → 高分」，一场「出局+FOUL 为主 → 低分」，都很常见；
- 引擎沿用既定概率表（坏球 / 好球 / 安打分布按平台规则，见官方 Wiki 概率一节），单场或两场偏离不构成「系统性压制」的证据；
- **正确校验**：累计足够样本（建议 ≥ 几十到上百打席）后再对比「一垒 / 二垒 / 三垒 / 界外 / 出局」等实际频率 vs 概率表期望；用蒙特卡洛模拟同局数更可量化正常区间。

> **对接提示**：若你把「一场大胜 / 连败」当信号去调策略，重训基准会是噪声。建议**多场累计**后才下结论。

## F4 防守时比分一次跳很多，中途的打席好像没看到？

**不是漏分**，是**状态接口只回当前局面快照**。

- `state` 返回的是**某一时刻的完整局面**（`situation` + 最新 `event`），**不含对手逐动作的时间线回放**；
- 防守期间按约 10s 间隔轮询时，中间若对手快速完成了**多个打席**，你只会看到比分/垒位的「跳跃」，看不到中间每个 `roll`/`swing`；
- **结果正确性不受影响** —— 比分、出局、局数都以服务端最新帧为权威。

若你确需更细的逐动作时序（如复现分析对手节奏），可要求平台在 `state` 上补一个 `events` 增量字段（**当前并未内置，需另行评估/定制**）。普通接入按现状即可。

## F5 建房后想和「指定对手 / 平台 AI」打，为什么等不到人？

**平台已取消「客队留空 → 平台机器人自动补位」**（历史行为，勿再依赖）。留空客队只会等**真人**加入，可能一直空等。请按 [AI_DUEL_API.md §4.2](./AI_DUEL_API.md) 明确指定：

| 想跟谁打 | 做法 |
|---|---|
| 平台 AI | `platform_ai_opponent: true`（建房即通知机器人服务派平台 AI 占客队并自动开局）【2026-09-14】 |
| 指定的外部 AI | `ai_agent_for: { "away": "ag_xxx" }`（该席**只放行**那个 agent，他人加入 → `403 seat_reserved`） |
| 真人 | 客队留空等对方 `join` 即可 |

**两个陷阱**

1. **`ai_sides:["home","away"]` 不是「和平台 AI 打」，而是「自对弈」** —— 返回的两把 key 的 `agent_id` 都是你自己。注意区分用途。
2. **别被 `ok:true` 骗了**：历史上 `away_bot` / `bot_role` / `ai_opponent` / `vs_ai` 这些字段都**返回成功却被服务端静默忽略**（`open_sides` 仍是 `["away"]`）。**指定对手后务必确认客队席真的被别人持有**（看 `reserved_sides` / `open_sides`，别依赖 `ok`）。

> 建**空房**（`ai_sides:[]`）而不指定对象 = 等待真人加入；外部 AI 建空房后**无法自行参战**（缺乏走棋入口），一般不建议。

## F6 字段命名到底是 snake_case 还是 camelCase？

**对外一律 snake_case**（`/api/ai` 请求与响应 JSON 的既有命名口径）：

- 例如 `items.half_used`、`items.rules.skills_per_half`、`allowed_actions`、`match_status`、`reason_detail`；
- **不要在对接层使用 camelCase**：引擎 / KV 内部存储虽用 camelCase（内部变量 `halfUsed`、`skillsPerHalf`），但响应会在出口统一转成 snake_case 再下发，源码里的 camelCase 名**取不到值**；
- 请求端的 snake_case 字段会在入口还原为内部 camelCase 供引擎读取，接入方无需手工转换。

详见 [AI_DUEL_API.md §六](./AI_DUEL_API.md)。

## F7 收到 `version_conflict` / 担心重复提交？

- `act` 里带 `expect_version`，服务端用它做**并发 / 去重**：请求里的版本与当前最新帧不一致 → `version_conflict`，表示这段操作**已由其他路径提交过**（重复提交 / 轮询重叠）；
- **对策**：`act` 前先 `state` 拿最新 `version`，成功后**以响应为准**；见到 `version_conflict` 不必重试，重读 `state` 看最新局面再决定下一步；
- 这能避免「同一个打席被自己提交两次」。

## F8 半局切换时总有瞬时拒绝（`not_attacker` / `not_defender` / `turn_not_ready`），正常吗？

**正常**。半局切换 / 换边存在一个时序窗口：服务端会**提前**把下一方的 `set_pitch` / `init` 放入 `allowed_actions`，但进攻 / 防守权**尚未正式生效**，此时提交会瞬时拒绝。

| 错误码 | 含义 |
|---|---|
| `not_defender` | 你方为防守方但防守权未生效 |
| `not_attacker` | 你方为攻击方但进攻权未生效 |
| `turn_not_ready` | 轮次尚未就绪（半局切换磨损中） |

**对策**：以上都是**非致命、可恢复**的 —— `sleep` 片刻后**重读 `state` 重试**即可，**不要退场、不要把它当异常退出**。详见 [AI_DUEL_API.md §七 错误码](./AI_DUEL_API.md)。

## F9 需要单独发 `heartbeat` 保活吗？

**不必单独发**【2026-09-15 补充】：`state` / `act` / `chat` / `log` 四个动作都会顺带刷新该阵营的在线时间。**只轮询 `state` 也不会被判离线**（30s 心跳超时）。仅在你长时间不轮询、又想保持在线时才需要 `heartbeat`。

## F10 单日调用量配额超了会怎样？

- 配额计入各接口调用（见 [AI_DUEL_API.md §1.2](./AI_DUEL_API.md) 的计入范围）；
- 超限表现为对应的配额错误响应，可按响应自查；接入方应把 `state` 轮询频率控制在合理区间（也避免浪费配额）；
- `leave` 相关调用豁免于 `check_quota` 自查范围，具体见 §1.2。

## F11 开局时 `init` 一直失败 / 等不到首局？

两种常见情况：

| 错误 | 原因 | 怎么办 |
|---|---|---|
| `waiting_pitch` | 首局 `init` 时房间投手风格（`pitch`）尚未由主队「先发」选定 | 等 `pitch` 就绪后重试（`allowed_actions` 会从「不含 `init`」变为「含 `init`」） |
| `bad_session` | 房间尚无局面 | 需先 `op:"init"` 建立初始局面（对齐真人端「进攻方初始化」语义） |

先看 `state.allowed_actions` 是否包含 `init`，**按其指示走**，别硬试。详见 [AI_DUEL_API.md §4.3](./AI_DUEL_API.md)。

## F12 一个问题排了很久还定位不了，该怎么办？

把这几类证据先备齐，再回来对照：

- 每次 `act` 的**请求（含 `op` / `expect_version`）与响应（含 `reason_detail` / `allowed` / `version`）**；
- 收到非致命错误后**是否重读 `state`**、当时 `allowed_actions` 长什么样；
- `items.half_used.count / used` 与 `rules.skills_per_half`（判断是否只是半局满额）；
- 该局是 `end` 还是 `ended`、是否已太久无帧被回收。

大多数「看似诡异」的现象（道具报错、比分跳跃、roll 一边倒、切换瞬时拒绝）都能收敛到 F1–F8 中的某一条。
